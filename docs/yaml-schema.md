# YAML scene format

The full schema for tact scene/robot YAMLs. AGENTS.md keeps only a one-paragraph
summary + pointer here. Worked examples: `demos/basic/arm2.yml`,
`demos/cartpole/cartpole.yml`, `fg/gos/gos.yml` (cameras), `fg/dog/dog.yml` (lidars),
`extras/envs/hf1.yml` (hfield).

Top-level keys: `sim` (`{solver: lcp, dt, g}` plus optional flat LCP knobs `erp`/`slop`/`cfm_scale`/`v_rest_thresh`/`iters`/`tol` — see "Global LCP solver knobs" below — `lcp` (Stewart-Trinkle/PGS with semi-implicit Euler) is the production contact solver. `solver: minimal` selects a test-only spring-damper ground-plane solver for spheres (`rbd.contact_ground_sphere`, Python step path). The legacy `penalty` spring-damper solver was removed 2026-05-24 — its brush friction could not hold a planted foot, and box stacking diverged at dt=1ms; archived in `_/penalty.c.removed-*`. A YAML with `solver: penalty` now raises a migration error), `view` (camera), `lights`, `materials` (contact-material library — schema below), `bodies`, `feeds`. Each body has `name`, optional `joint` (`type` ∈ `rev|lin|free|fixed`, plus `parent`, `pos`, `euler`, `eulerseq`, `damping` (viscous), `spring`, `frictionloss` (per-DoF Coulomb friction bound, N·m for rev / N for lin — rev/lin only, default 0=off; solved as an LCP constraint row, NOT folded into ABA — see "Contact solver" below and `docs/design-joint-friction.md`), `armature` (per-DoF rotor/reflected inertia à la MuJoCo, kg·m² for rev / kg for lin, default 0=off; a constant added to the M diagonal AND the ABA articulated inertia `d`, so the predictor and contact solve agree — reflected inertia = rotor·gear². Verified `qdd = τ/(I+armature)` to machine ε; `tests/test_joint_armature.py`), `limit: [lo, hi]` (joint range — **degrees for rev / m for lin** (same convention as `q0`; stored internally in rad/m), default absent = unlimited; limited iff `lo<hi`. Solved as a one-sided LCP constraint row when the joint reaches a bound — a "contact normal" on the joint coordinate, λ≥0 + Baumgarte; rev/lin only, v1. `tests/test_joint_limit.py`), and `q0`. **`k: [kp, kd]` was REMOVED 2026-06-07** — implicit joint-PD gains are control-policy inputs, not plant parameters, and mode-switching controllers need per-mode values, so they pass per step instead: `env.step(kp=, kd=)` / `Model.step(kp=, kd=)`, with `start` reading the controller's `kp`/`kd` attrs every tick. A YAML with `k:` now raises a migration error. The mujoco backend takes the same per-step gains (mjenv writes them into the position actuators' gainprm each step — the XML kp/kv are structural placeholders); on real the gains live in the driver/firmware (capability ledger)), `inertial` (`mass`, `tensor` with first element `zero|diag|sphere|z-cyl|box`), `shapes` (visual + contact: `type`, `param`, `pos`, `euler`, `contact: [pair_id, mat_name]`, and color as `rgba: [r,g,b,a]` where `a` is opacity in [0,1] — `a<1` renders translucent via back-to-front alpha blending in both `win_render` and `egl_render` (opaque pass with depth-writes on, then translucent objects sorted far→near by `sort_transparent` and drawn with depth-writes off; each translucent object is additionally drawn in two culled passes — far/back faces then near/front faces, `draw_translucent_object` — so a single closed convex mesh blends its own surfaces in the right order and doesn't show sawtooth seams along its silhouette); `a` is optional and defaults to 1.0, so `rgba: [r,g,b]` is accepted as opaque; stored as a width-4 `crgba`; `rgba[0]<0` is the render-skip/non-raycast sentinel. The legacy `rgb` key was unified into `rgba` 2026-05-25 and is no longer read — a stale `rgb:` is silently ignored, leaving the shape invisible), and `frames` (named coordinate frames addressable via `model.fk`/`fkh`). The body named `root` is the world; renaming via `base != 'root'` prefixes it with `*`. `demos/basic/arm2.yml`, `demos/cartpole/cartpole.yml`, and the background scene files in `extras/envs/` (`1.yml`–`5.yml`, `box1.yml`, `desk1.yml`) are good worked examples.

**`cameras` library** (top-level list, parsed in `sim.py`): declares publish-able cameras so `start` auto-publishes them over ZMQ (replacing the imperative `-z` flag). Each entry: `{name, type, body, pos, euler, res, vfov, fps}`. A camera **is a frame plus publish metadata** — at parse time each camera is injected as a named frame (= `name`) attached to `body` (default `root`) at `pos`/`euler`, so it reuses the full frame machinery (default-fill, root-offset, fdict/fbody registration, add/delete group handling) and `env.camera_frames()` / `env.lidar_frames()` resolve it. Use `body: <link>` to attach a camera to a moving link (e.g. a wrist camera). Publish metadata is kept in `model.cameras` / `env.cameras` (list of `{name, type, res, vfov, fps}`, `name` carries the add-prefix to match its fdict key). `type` ∈ `rgb` | `depth` (validated at parse). Encoding lives in `env.camera_frames()` (the per-type getters were inlined 2026-06-06): `rgb` → JPEG bytes; `depth` → zstd-compressed little-endian float32, row-major top-to-bottom, **linear eye-space distance in meters** (no-geometry pixels read the far plane, 200 m) — both via `egl_render` (`opt=1`/`opt=2`). Decode depth: `np.frombuffer(zstandard.decompress(buf), '<f4').reshape(h, w)`. `res` `[w, h]` (default `[640, 480]`) is honored: it is forwarded to `egl_render`, which sizes its pbuffer / resolve-FBO / CPU scratch / JPEG buffer to it. Sizing is **grow-only** (a request larger than any seen so far reallocates; smaller requests reuse the capacity and just viewport/read the actual size), so a mix of camera resolutions stops reallocating after the first frame at the largest one. `vfov` (deg, default `45`) is the **vertical** field of view (MuJoCo `fovy` convention), forwarded to `egl_render` and used as the perspective `fovy` (horizontal extent follows from the `res` aspect ratio). `fps` (Hz) sets the per-camera publish cadence (`cycle = round((1/dt)/fps)`). `fg/gos/gos.yml` is the worked example.

**`lidars` library** (top-level list, parsed in `sim.py`): the **virtual LiDAR** counterpart of `cameras`, kept as a **separate key** because LiDAR diverges from cameras in enough ways (ray-based not raster, range-along-ray semantics, future point-cloud output) that sharing one block would be awkward. Each entry: `{name, type, body, pos, euler, eulerseq, res, dth, fps, pinhole, perpendicular, max_range}`. Like a camera, a lidar **is a frame plus publish metadata** — at parse time the shared `_register_sensors` helper (`sim.py`) injects it as a named frame attached to `body` (default `root`), so it reuses the full frame machinery (default-fill, root-offset, fdict/fbody registration, add/delete group handling — tracked in the group ledger as `nlidars`, parallel to `ncameras`). Publish metadata is kept in `model.lidars` / `env.lidars` (`name` carries the add-prefix to match its fdict key). The defining difference from cameras: rendering goes through the CPU raycast pipeline (**`env._ray_grid` + `tact_raycast_frame`**, composed inside `env.lidar_frames()`; the public `raymap`/`raycloud` wrappers were inlined 2026-06-06), not `egl_render`. `type` ∈ `2d` | `3d` (validated at parse). Encoding lives in `env.lidar_frames()` (the per-type getters were inlined 2026-06-06); the lidar wire is **RAW little-endian float32, no compression** (Python-side zstd removed 2026-06-06: floats compress only ~x1.5 at real sim-loop cost, and /dev/shm IPC has ~1000x headroom — note depth CAMERAS still arrive zstd-compressed, C-side). `2d` → row-major top-to-bottom depth map (decode: `np.frombuffer(buf, '<f4').reshape(h, w)` with `(w,h) = res`); values are **range-along-ray in meters** (LiDAR convention) with **`-1` for pixels that hit nothing** (vs. a depth camera's 200 m far plane). `3d` → **`(N, 3)` points in sensor-frame coordinates** (decode: `np.frombuffer(buf, '<f4').reshape(-1, 3)`); `N` varies per frame — no-hit rays are dropped, and `max_range` (m, optional, default unlimited, 3d-only) drops far hits. Points are range-along-ray back-projections (`perpendicular` doesn't apply to 3d). The consumer composes the lidar's frame extrinsic (this entry's `body`/`pos`/`euler` — the single source of truth in sim and on hardware) with its own pose estimate to place points in the world, so a real-hardware lidar driver publishing the same wire format is a drop-in replacement. `res` `[w, h]` (default `[120, 80]`). `dth` (deg/pixel, default `1.0`) sets the angular resolution; horizontal FoV = `res[0]·dth`. `pinhole` (default `false` = angular/equirectangular projection, the LiDAR convention) and `perpendicular` (default `false` = range along ray; `true` = camera-Z depth so flat planes stay flat) shape the 2d ray pipeline. `fps` (Hz) sets the publish cadence (`cycle = round((1/dt)/fps)`). `fg/dog/dog.yml` is the worked example. (Both `cameras` and `lidars` may later unify under a broader `sensors:` key.)

**`tactiles` library** (top-level list, tact `Env` only in v1): surface-taxel tactile arrays. Each entry attaches to a body and declares explicit body-local taxel centers and local surface frames. Required: `name`, `body`, and either inline `samples` or `samples_file`. Optional: `cell: [du, dv]` declares each taxel's rectangular surface footprint in the sample's `tangent_u`/`tangent_v` directions; when present, 2-point contact manifolds are integrated as line segments and 3+-point manifolds as contact patches over taxel cells. `radius` (default 0.003 m) is the taxel receptive margin: point-like contacts use it as the splat radius, while segment/patch contacts inflate each taxel cell by this margin before overlap integration. Other optional fields: `fps` (default 500), `filter_tau` (default 0, seconds; exponential low-pass time constant applied once per published frame), `kernel` (`gaussian` default, `linear`, `nearest`), `sigma` (default `radius*0.5`), `channels` (default `[normal, shear_u, shear_v]`; also `pressure`). A sample row is `x y z nx ny nz ux uy uz [area]`, where `normal` is the outward body-local taxel normal and `tangent_u` is orthonormalized against it; `tangent_v = normal × tangent_u`. CSV/TXT files may include a header and `#` comments. `env.tactile_frames()` maps the last LCP contact reports to these samples and publishes raw little-endian float32 `(N,C)` over `/dev/shm/<name>`. `normal` and `pressure` are positive under compression; shear channels keep signed body-local force components.

**Sensor frame convention (cameras + lidars):** a sensor views along its **frame's -Z** axis, and both paths apply the same **-90° roll about -Z** — the camera path in `camera_frames` (frame pose post-multiplied by `Rz(-90°)` before `egl_render`), the lidar path in `Env._ray_grid` (the roll is folded into the ray directions; C's `tact_raycast_frame` is a pure intersector) so the two are unified: a camera and a lidar at the same frame `pos`/`euler` produce the identically-oriented image (verified camera-depth vs lidar-range, corr=1.000). Consequence: on a Z-up body (e.g. a quadruped `base`), euler 0 points -Z straight **down**, and an **upright, forward-looking** sensor pitched α° down is a **pure Y rotation** `euler: [0, α-90, 0]` (`[0,-90,0]` horizontal, `[0,-70,0]` 20° down, `[0,-60,0]` 30° down). `rz` is a world-Z yaw, not a view-axis roll, so don't use it to fix image roll — the -90° roll is already baked in.

**`materials` library** (parsed in `sim.py`): a named dict of contact-material specs; a shape selects one by name via `contact: [pair_id, mat_name]`. `pair_id < 0` → shape is non-collidable (material name then optional); two collidable shapes form a contact pair only if both `pair_id ≥ 0` and not *both* are `0` (so `0` collides only with nonzero groups). Each material groups parameters by physical concept:
```yaml
materials:
  <name>: {normal: [k_n, d_n], tangent: [k_t, d_t, mu], spin: [k_spin, d_spin, mu_spin], roll: [k_roll, d_roll, mu_roll], restitution: e}
```
The four groups (`normal`/`tangent`/`spin`/`roll`, 11 values total) are **mandatory**; `restitution: e` (coefficient of restitution) is an **optional scalar**, default `0.0` = fully inelastic (the pre-2026-05-25 hardcoded behavior). The parser flattens each material to a 13-vector `[pair_id, k_n, d_n, k_t, d_t, mu, k_spin, d_spin, mu_spin, k_roll, d_roll, mu_roll, e]`, which is the C-side `cparam` row layout. When two materials meet at a contact, the 11 stiffness/damping/friction values are **arithmetic-averaged** but restitution is combined by **`min(e_i, e_j)`** (the more dissipative surface caps the rebound; min also reproduces `e` for identical materials). `mu` is per-material (no global friction constant). `demos/basic/sphere_test.yml` and `demos/box-wall/box_wall.yml` show material use.

**Global LCP solver knobs** (flat under `sim:`, all optional — defaults = historical hardcoded values, `lcp` path only): `erp` (0.2, Baumgarte penetration correction), `slop` (1e-4 m, penetration deadband), `cfm_scale` (1e-6, CFM regularization scale; `R_diag = cfm_scale/(k·dt²+d·dt+ε)`), `v_rest_thresh` (3e-2 m/s, restitution velocity gate — below it restitution is suppressed so resting contacts settle), `iters` (20, PGS max sweeps), `tol` (1e-6, PGS convergence on max|Δλ|). `erp`/`cfm_scale` mirror ODE's ERP/CFM. These are per-sim (not per-material): they thread through both step paths identically — Python via `contact_lcp(...)` kwargs, C via `tact_create` (stored in the handle, used by `tact_step_lcp`). Set on `Model` at parse time (`self.erp` etc.).

Shape `param` follows MuJoCo's half-extent / half-length convention:
- `box`: `[hx, hy, hz]` — half-extents along each axis (full edge length = `2*h`)
- `sphere`: `[r]`
- `cylinder`: `[r, hh]` — radius, half-height along local z
- `capsule`: `[r, hh]` — radius, half-length of the cylindrical section (hemispherical caps add another `r` at each end)
- `mesh`: **uses `file:` not `param:`**. `{type: mesh, file: meshes/x.obj, ...}` — path is resolved against the YAML file's directory when relative, or used as-is when absolute. Python's `Model.add()` dedups by absolute path and assigns an internal slot id (`mesh_path_to_idx`); C side has 64 slots total (`MAX_MESH` in `shape.h`). Per-slot vertex storage is dynamically allocated by `load_obj()` (`shape.c`) from the OBJ file size (no `MAX_VERTEX` cap — earlier 1024-vertex fixed buffer silently truncated meshes like the bundled `10.obj` at 2562 verts). `add()`/`delete()` do not free slots, so churning many distinct paths can exhaust the slot table — that's a hard error.
- `hfield` (height field, terrain): **uses `file:`/`data:` + `size:` not `param:`**. `{type: hfield, file: hf1.bin | data: [[...],...], size: [sx, sy, sz]}` — `file:` is a height grid in **MuJoCo's custom hfield binary** (int32 nrow, int32 ncol, float32 data[nrow·ncol], row-major, row i→+Y col j→+X; resolved against the YAML dir; read by `tact.load_hfield`), or inline `data:` (nested list); `size: [sx, sy, sz]` gives XY half-extents (m) and a height scale `sz` (heights *= sz; use 1 for a grid already in meters — tact does NOT normalize, unlike MuJoCo's [0,1] normalization of the same file). One data file under `tact/extras/envs/` serves both the tact YAML and the MuJoCo twin scene (`extras/mjcf/hf1.xml`). Python loads/scales the grid and pushes it to a C slot via `clib.set_hfield_data` (slot stored in `cshape[0]`, like mesh; `MAX_HFIELD=16` in `shape.h`). Contact: sphere-hfield + box-hfield supported (Tier 1/2); raycast (height_scan/lidar/depth) via 2D-DDA `ray_intersects_hfield`. See `docs/design-hfield.md` and `extras/envs/hf1.yml`.
